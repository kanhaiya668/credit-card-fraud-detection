# Vigil — Credit Card Fraud Detection

An end-to-end fraud detection system: data pipeline → model comparison →
Flask web app with single-transaction check, bulk CSV scoring, and a
results dashboard.

Built on the [Kaggle Credit Card Fraud Detection dataset](https://www.kaggle.com/mlg-ulb/creditcardfraud)
(284,807 European card transactions, 492 confirmed fraud cases — 0.17%).

## Why this project

Fraud detection is a genuinely hard ML problem, not just because of the
modeling, but because of the data itself:

- **Severe class imbalance** (0.17% fraud) — accuracy is a useless metric;
  a model that never flags anything is 99.8% "accurate."
- **Anonymized features** — V1-V28 are PCA components, so there's no
  manual feature inspection to lean on; the model has to find the signal.
- **Asymmetric cost of errors** — a missed fraud case and a false alarm
  on a legitimate customer are not equally bad, which shapes how the
  model is evaluated (PR-AUC, not accuracy) and how a real system would
  set its decision threshold.

## Pipeline overview

1. **Clean**: drop ~1,081 duplicate rows (prevents train/test leakage)
2. **Engineer features**: `scaled_amount` (RobustScaler), `amount_log`
   (log1p, compresses the long tail), `hour_of_day` (derived from `Time`)
3. **Split**: 80/20 stratified train/test split — the split happens
   *before* any resampling, and the test set is never touched by SMOTE
4. **Resample**: custom SMOTE applied to the training set only, bringing
   fraud from 0.17% up to ~13% of the training data (not fully balanced
   to 50/50 — that would mean ~280k synthetic rows from ~400 real ones,
   which is slow and prone to overfitting on synthetic noise)
5. **Train & compare**: Logistic Regression (baseline), Random Forest,
   and HistGradientBoosting (scikit-learn's native gradient boosting —
   the same family as XGBoost/LightGBM)
6. **Select**: best model chosen by **PR-AUC** (precision-recall AUC),
   the right metric when the positive class is this rare
7. **Save**: model + scaler + a full metrics report to `models/`

## Results (on a held-out test set of 56,746 transactions)

| Model | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|
| Logistic Regression | 5.3% | 87.4% | 0.10 | 0.962 | 0.690 |
| Random Forest | 73.8% | 80.0% | 0.77 | 0.976 | 0.798 |
| **HistGradientBoosting (selected)** | **90.4%** | **79.0%** | **0.84** | **0.969** | **0.812** |

The selected model catches ~79% of fraud in the test set while keeping
false alarms low enough that 9 out of 10 fraud alerts it raises are real
(90.4% precision) — a workable trade-off for a system where every false
alarm means a real customer's card gets flagged.

## Setup

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Place the Kaggle dataset at data/creditcard.csv

# 3. Train the model (takes ~5 minutes, mostly the Random Forest)
cd src
python train_pipeline.py

# 4. Generate the app's demo data (sample transactions + dashboard stats)
python generate_app_assets.py

# 5. Run the web app
cd ../app
python app.py
```

Then open **http://127.0.0.1:5000**.

## Using the app

- **Check transaction** — enter a transaction's details, or click
  "Load random sample" to pull a real transaction from the test set
  (the V1-V28 features are anonymized PCA values, so typing realistic
  numbers by hand isn't practical — the sample loader solves that).
- **Bulk upload** — upload a CSV with columns `V1`...`V28` and `Amount`
  (the raw Kaggle format with `Time`/`Class` also works — extra columns
  are ignored) to score every row at once, with a downloadable results CSV.
- **Dashboard** — model performance metrics and dataset patterns
  (fraud rate by hour, amount distribution) in one view.

## Notes on the SMOTE implementation

`imbalanced-learn` wasn't available in the build environment, so
`src/custom_smote.py` implements SMOTE from scratch on top of
scikit-learn's `NearestNeighbors`, following the original 2002 paper:
for each minority-class sample, find its k nearest minority neighbors,
then generate a synthetic point by interpolating along the line to a
randomly chosen neighbor. This keeps synthetic fraud examples inside
the real data's minority region instead of just duplicating rows.

## Possible extensions

- Threshold tuning per business cost (a false negative likely costs
  more than a false positive in most real fraud systems)
- SHAP/feature-importance explainability on individual predictions
- A feedback loop where confirmed fraud/false-positive labels get
  folded back into retraining
